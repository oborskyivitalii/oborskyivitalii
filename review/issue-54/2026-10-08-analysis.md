## Decisions and target architecture

The user authorized this guide/audit/plan and its normal issue/Draft-PR workflow.
No new framework, runtime package, redesign, content rewrite or blanket history
cleanup is proposed. Preserve public URLs, wording/editions, semantic HTML/SEO,
navigation/history, static/offline reading, camera/fractal positions, visual
appearance, safety bounds and existing performance budgets.

| Responsibility | Proposed owner after migration | Input → output |
| --- | --- | --- |
| Records, route metadata and labels | Existing `site/content/catalog.json` and a bounded route/label schema in `site/content/` | Validated stable records → render/runtime view models |
| Prose and page composition | `site/content/pages/<route>/` | Markdown/bounded rich text plus explicit block references; no executable expressions |
| Repeated page/card structure | `site/templates/` | Escaped validated view model → semantic HTML |
| Shared palette/layout/reading appearance | Existing `site/engine/*.css`; component/effect CSS alongside its owner | Tokens/variants → hosted and offline CSS from identical authored bytes |
| Reusable Color effect implementation | Proposed `site/effects/` | Explicit factory + CSS source + controls/descriptor → delivery adapters |
| Navigation, session lifecycle, math/projection/render | Existing `site/engine/` with cohesive extractions only as needed | State + scene data → bounded draw/DOM updates |
| Scene-specific geometry and camera parameters | Existing `site/scenes/` | Typed/documented model units and finite bounds → pure geometry/poses |
| Source discovery and assembly | `tools/site/` | One maintained active-source/effect manifest → hashes, bundles, offline/hosted variants, scanner inputs |

Dependencies flow from content/models and explicit effects into build adapters;
the output is `docs/` and existing declared standalone renditions. Runtime must
not depend on build tools or generated copies. A manifest declares source paths
and capabilities; it is not a universal bag of content, CSS values and mutable
state. Each concern retains one local authoritative owner.

R1 is the recommended first Sol assignment. Its extraction seam also helps the
future fragment-flight work, but it must not implement that feature incidentally.
If moving files and replacing extraction become too large together, land a pure
move with updated consumers first, then the descriptor adapter in its own PR.
Likewise R3 migrates one component/page as a proof of contract before broad conversion.

Acceptance pattern for each execution issue:

1. Named behavioral/semantic parity outcome with affected source owners.
2. Code-style AC naming applicable CS01–CS10 rules, bounded automatic selectors,
   manual review and exact permitted debt/removal task.
3. Source inventory/RI/check routing and generated artifact identity updated.
4. Relevant resource budget result, where changed, and honest exact-source review.

Sol is an appropriate execution role for these bounded migrations. The primary
agent should review the architecture seams, content migration equivalence and
performance evidence between PRs. A single instruction to "make all code clean"
would leave too many contracts implicit. This is a work-allocation recommendation,
not a benchmark claim about model capability. No delegation has started.
